0.13.0 — 2026-09-04

Added

  • On the dashboard, t on a GitHub issue opens the transcript of the ticket the bridge built for it — live-following while the run is in flight — so a labeled issue can be watched without hunting for its row in the queue section (#330). Works from the issue list and from the open issue detail view; a toast explains when nothing is in flight for that issue (enter still opens the issue body).
  • Apply tickets: a ticket body carrying a junco-patch fence (a git format-patch mbox series) executes with zero model turns — git am --3way applies AND commits the series directly in the worktree, so the series' own commit messages become the PR's commits, in order. Verification (## Verification) still runs and still gates the PR; the critic pass is skipped, since the diff already is the spec. A conflict fails the ticket outright rather than requeuing it (a conflict is deterministic, not transient), with the git am output folded into the failure note and the worktree preserved for inspection. New junco lint/submit --dry-run rules: patch_parses and patch_paths_sane (errors — a malformed series, or one touching traversal/absolute paths or carrying a binary hunk) and patch_has_verification (warning); the prose rules are skipped for these tickets. See Apply tickets.
  • Apply tickets gain a one-shot escalation ladder, gated by worker.applyFallbackToAgent (default true): a failed git am --3way, or a clean apply whose ## Verification block then fails, dispatches exactly one agent session instead of failing the ticket — the patch series handed to the agent as a specification to implement against the current tree, plus the failure detail, never as bytes to replay. Because a fallback breaks the GitHub route's byte-identical approval guarantee (a human's trigger label approved a specific diff, not whatever the agent produces instead), the PR body carries an explicit disclosure banner whenever it fires, and the critic pass — skipped on a clean apply — runs again once an agent has touched the ticket. Set the lever to false for the old hard-failure behavior. See Tickets § Escalation ladder and Configuration § Apply-ticket fallback.
  • junco submit --patch <file> --repo <path> [--title T] [--why W] [--verify CMD] composes and submits an apply ticket directly from an existing git format-patch file — no hand-authored junco-patch fence required — and composes into the same --as-issue/--dry-run routing as a file-sourced ticket.
  • The junco-dispatch skill now teaches apply-mode authoring: a drafting-time mode question (does the agent already know the exact bytes to land?), a dedicated "Apply mode (patch tickets)" section covering how to produce a series, the fence-length rule, when not to use it, and what the fallback means for the byte-identical guarantee, plus a minimal apply-ticket shape in TEMPLATE.md.
  • Apply-ticket execution now shows up in observability: each pull-request-kind task-history record (<dataDir>/data/history/tasks-YYYY-MM.jsonl) carries a mode field — "apply" (clean apply, no fallback), "apply_fallback" (either escalation rung fired), or "agent" (an ordinary agent-driven ticket) — so the wall-clock/token difference between modes is queryable instead of inferred from logs. Apply runs also now write a transcript: junco_meta + a junco_run_start (flow: "apply") + a junco_run_end frame bracket the git am attempt on both the success and the failure path, and a failed-then-escalated ticket's fallback session appends to the same file — one chronological record, not two.
  • Apply tickets can now be claimed while the inference endpoint is unreachable or the provider gate is latched — claimNextTask narrows an otherwise-blocked claim pass to just the eligible apply tickets instead of leaving the whole inbox untouched, since git am needs neither the endpoint nor a provider quota. The daemon's startup endpoint wait is unaffected (this narrowing is per-claim only), and a claimed apply ticket whose patch then fails to apply can still fail on the fallback's own agent session being unable to reach the same downed endpoint — cleanly, bounded by the existing transient-retry cap. See Operations § Inference endpoint unreachable at boot.
  • End-to-end test layer (npm run test:e2e, run in the quality gate): the built CLI runs as a child process in a sandboxed HOME with the real agent SDK driven against a scripted OpenAI-compatible model stub — PR happy path, read-only Q&A, transient-failure requeue, and daemon lifecycle (start, /health, poll-driven drain, SIGTERM) — and scripts/package-smoke.sh now runs the PR scenario through the tarball-installed binary. npm run test:e2e:live runs the same harness against a real inference endpoint (JUNCO_E2E_MODEL_ID / JUNCO_E2E_BASE_URL / JUNCO_E2E_API_KEY).
  • SECURITY.md gives junco a disclosure channel (#383): the supported version window, reporting through this repository's private vulnerability reporting with a 72-hour acknowledgement, and the four in-scope boundaries — the execution sandbox, the GitHub bridge's approval chain, bot-account auth, and the health endpoint — alongside an explicit out-of-scope list, so a reporter knows up front what will and will not be treated as a vulnerability. A pull-request template and an .editorconfig land beside it.
  • .nvmrc pins the exact engines floor (22.19.0), so nvm use and anything else that reads it lands on the version CI treats as the floor, and the quality gate gained a non-blocking node 26 canary leg (#382). Node 26 becomes LTS in October 2026 while the gate otherwise exercises only 22.19 and 24; the canary annotates a run but is deliberately kept out of the aggregate quality-gate job, so it can never block a merge.
  • Plan sets are documented, and two new ticket templates ship in the package. Plan sets landed in 0.12.0 behind [planSets], but a reader of docs/ could not find the section, its three levers, or the junco-plan fence they actually write (#375). Configuration § Plan sets now covers the levers and the fact that the Layer-1 depends_on machinery stays on with the lever off, and Tickets § Plan sets covers the local and bridge doors, a minimal fence, the field table, and what the compiler builds and refuses. examples/apply-ticket.md and examples/plan-set.md join the shipped examples, checked against the real parsers by the suite so a compiler or lint change cannot break them silently.
  • Every version heading in this file resolves to its tag diff (#374). The file declared Keep a Changelog conformance, but the [x.y.z]: reference block that resolves the headings never existed — so on npm and GitHub all sixteen rendered as literal bracket text. A release that adds a heading without its link now fails the gate.
  • Per-repo chat with the coding agent inside the dashboard (t on a repo row): an ongoing, read-only conversation, file-backed and daemon-owned so it survives a dashboard quit or a daemon restart. Every dispatch branch is reachable from it — a plain ticket, a ticket set, a plan set, an amend on an open PR, an apply-ticket patch, or a request to audit/investigate — each parked for the same human confirm audit/investigate findings already use (s submit, e edit, r cycle route, D discard). New config block chat.* (chat.enabled, chat.modelId, chat.thinkingLevel, chat.turnTimeoutMinutes); new data-tree dirs data/chats, data/chat-drafts; new loopback-only /chat/* routes on the health server (GET /chat/events, POST /chat/prompt, POST /chat/abort, POST /chat/new, POST /chat/note, GET /chat/status); junco transcript --chat <owner/repo> prints a session's transcript outside the TUI.
  • The dashboard chat can now submit the work it drafts. Asking the agent to submit/queue a parked draft makes it call its one action tool, junco_submit, which proposes the submission as a card in the chat — y runs the same junco submit the card's s does (inbox, or --as-issue), n keeps the draft parked — and the agent's turn waits for the answer (its own timeout paused) so it reports the real outcome in the same reply. /submit [id] in the composer submits a parked draft directly. New levers chat.submitTool (default on) and chat.confirmTimeoutMinutes (default 10); new transcript record junco_chat_command; new loopback route POST /chat/decide. The agent's file tools stay read-only and it still cannot run a shell; nothing else on the dashboard is reachable from the chat.
  • Dashboard chat: the header's cost figure is now today's chat spend rather than the daemon's lifetime total — /health.chats gains chatTodayUsd, a chat-only bucket the manager rolls over on the spend ledger's own day boundary (the ledger stays single-writer; the amount is deliberately chat-only, since the ledger's day bucket counts ticket runs too), and the label reads chat $X today again (#456). The in-pane hint row under the transcript is gone — the two-row shortcut bar already lists those keys — and its one unique piece of information, the window indicator, moves to the header's right edge beside the follow state (following / paused), giving the reclaimed row to the transcript (#471).
  • The junco_submit card no longer claims to be awaiting you while the CLI is still running. The moment y releases the tool into junco submit, the daemon records an additive running status on junco_chat_command; the card reads ▸ submitting …, y/n are disarmed, and the header says ▸ submitting… (#478). The record is the honest one: it survives a reconnect, and a daemon crash mid-submit resolves it as expired (daemon restarted) exactly like a proposal. The handshake is also now pinned inside a real turn — a fake session that actually invokes the tool proves the aborted record lands before junco_chat_turn_aborted, that the turn deadline pauses while the tool blocks, and that abort() fires the SDK's own per-call signal (#477).
  • A chat turn that was soft-aborted — /abort, the per-turn timeout, a daemon stop — no longer drops a draft it had already finished emitting: a complete, closed fence is parked with a warning row (emitted before the turn was aborted) so s still works; an unclosed fence is never parked, and an aborted turn never starts the auto-lint follow-up (#454). Parity with the PR flow, where a guard kill still salvages the commits into a PR.
  • The dashboard has a process-level safety net: an unhandled promise rejection is written to the worker log and surfaced as a toast instead of the hard quit with no message that Node 22 would otherwise perform (#455).

The preview itself is now codified as a curated essence — key design decisions, a Files/Steps summary, and the dry-run's destination/reason/carried/discard/timeout lines — plus the temp-file path for full reading, never the raw ticket body.

Security

  • A ticket's ## Verification bash blocks now run under the same sandbox backend and policy as the agent's own bash (#335). They previously spawned as a bare /bin/bash -c with only the environment scrub applied — no OS confinement, unrestricted network, the whole filesystem — while executing whatever the agent had just written into the worktree: a package.json script, a Makefile target, a conftest.py. Tokens were scrubbed from the environment, but the bot's gh credential, ~/.ssh, and every other checkout on the host live on disk and stayed reachable. Blocks now get network per sandbox.network and the per-ticket network: opt-in, writes limited to the worktree, its scratch dir, the linked worktree's git metadata and sandbox.extraAllowWrite, and TMPDIR redirected into scratch. The sandbox is resolved lazily (a block-less ticket never pays for the probe) and once per ticket, and a resolver failure fails every block closed rather than running it unconfined. The new live-reload lever verify.sandboxed (default true) opts out, and is inert when sandbox.enabled is false. See Configuration § Verification sandbox.
  • The sandbox's builtin read deny-list now covers the standard credential files (#336). The read side is "the whole host minus a short list", and that list stopped at ~/.ssh, ~/.aws, ~/.config/gh, ~/.gnupg and ~/.pi — so on every ticket the agent could read ~/.npmrc, ~/.git-credentials, ~/.netrc, ~/.docker/config.json, ~/.kube, ~/.config/gcloud, ~/.cargo/credentials.toml, ~/.pypirc, ~/.gem/credentials and the coding-agent harness's own home directory. The list is not operator-removable, as before.
  • junco now scans the diff it is about to push and refuses the push on a hit (#337). sandbox.network: deny governs the agent's tool calls; it is never consulted when junco itself runs git add -A over the worktree and pushes under the bot identity — so the push was an egress channel no sandbox rule saw, and content copied into a source file left the host through junco's own privileged push.   • junco ask, junco audit and junco investigate can no longer write to the checkout they read (#346). All three run the agent in the operator's real checkout, and the sandbox policy made that cwd a writable root unconditionally — the read-only promise rested entirely on the tool allowlist. A locally dispatched ticket's tools: is used verbatim, so one naming bash or write silently turned a read-only run into full write access to the live checkout, .git included: two layers that should be independent were one. The three flows now build their policy with scratch as the only writable root, so the in-process path jail and both OS backends refuse writes into the checkout whatever the allowlist says. Reads of the checkout are unaffected, and the PR flow and the critic keep their existing policy.
  • An apply ticket's patch series can no longer reach git am with a path junco never inspected (#338, #339). The containment check — traversal paths, absolute paths, binary hunks — was enforced only by plan-lint's patch_paths_sane rule, which runs only while planLint.enabled and planLint.blockOnError are both on, both live-editable levers an operator may plausibly turn off for the style rules. With lint off, a series naming ../escaped.txt reached git am, and git's own rejection rolled into the escalation ladder, which by default handed the series to an agent as its "reviewed" specification. applyPatchSeries now runs the same checks itself, unconditionally, before any side effect — no temp file, no transcript frames, no git call — and the ticket fails with apply failed: refused before git am: … regardless of the fallback toggle. Until now a host with no bwrap, or a kernel that refuses unprivileged user namespaces, silently degraded the session to the none backend: the environment scrub and the in-process path jail survived, but agent bash ran with no OS confinement while junco status looked healthy and only a log warning and a junco doctor warn: said otherwise. With the lever on, an unavailable auto-selected backend refuses the session outright and junco doctor reports ✗ sandbox and exits 1; both refusal messages name the lever, since it is the opt-out rather than sandbox.enabled. It is inert for an explicitly named backend and for backend: "none", which already failed closed. See Configuration § Sandbox backend.
  • The GitHub bridge now vouches a sub-issue's parent body against the trigger label, not just the child's (#342). When a labeled issue is a sub-issue, the bridge injects the parent's title and body into the planner prompt as background context — but only the child was checked by the edited-after-label guard, and the parent is a different issue with a different author that could be edited at any time after the label vouched the child. The same lastEditedAt check now runs at the parent's own repository and number (sub-issues may live across repos); a parent that postdates the label, cannot be verified, or is missing its coordinates has its context dropped with a warn log line. A failed parent check never blocks the child, which was vouched on its own.
  • The final issue comment junco posts at finalize — the Q&A answer, or the PR-link excerpt — is sanitized before it is published (#341). It carried the model's text verbatim, and junco recovers plans by looking for a <!-- junco:plan --> marker in its own bot-authored comments, so a prompt-injected agent could plant a forged marker on the very issue the plan flow reads back. The text now goes through the same sanitizer the parked audit and investigate drafts already use — HTML comments and control characters stripped, capped at the comment limit — and an answer that sanitizes to nothing falls back to the existing _(no answer text)_ placeholder.
  • The data tree is created private: 0700 on the root and every subdirectory, 0600 on config.json and on transcript .jsonl files (#343). On a shared or multi-account host, every local user could previously read the config — which may hold a literal model.apiKey — and every transcript under the data root, which is the full agent event stream including verbatim contents of private-repo files; all of it was created under the default umask. The mode rides the temp file through the atomic rename, so a rewrite tightens a loose file too.   • Sandbox reads are now deny-by-default across the junco data tree.
